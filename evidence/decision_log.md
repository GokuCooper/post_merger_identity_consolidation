# Decision log

Every choice that a reviewer or interviewer might ask "why?" about. One line each, filled in as you go.

| Day | Decision | Options considered | Why this one | Revisit when |
| --- | --- | --- | --- | --- |
| 1 | Forest wide authentication on the trust | Forest wide, selective | Lab needs broad access to test; a real merger would start selective and open server by server | Before any real merger |
| 1 | Domain Local group for cross forest access (DKN_Projects_Readers) | Global, Universal, Domain Local | Only Domain Local groups can hold members from another forest | Never, this is how AD works |
| 1 | SID history across the trust uses /enablesidhistory:yes, not /quarantine:no | quarantine, enablesidhistory | SIDFilteringQuarantined only applies to external trusts; forest trusts use enablesidhistory | Enabled on Day 3. Turn off after shares are re-permissioned |
| 2 | Custom schema attribute dknSourceCompany (Unicode String, single value, 1 to 64 chars, OID from the Microsoft prefix plus a GUID) | New attribute, reuse extensionAttribute, use company field | extensionAttributes are often already claimed by Exchange or other apps, and company describes the current employer, not where the identity came from. A dedicated attribute has one clear meaning. Schema changes are permanent, so a DC snapshot was taken first | Day 4, when it syncs to Entra as a directory extension |
| 2 | Separate OU tree for acquired assets (OU=Acquired, OU=Peachtree with Users, Groups, Servers, ServiceAccounts) | Mix Peachtree objects into existing DKN OUs, separate tree | Lets merger GPOs target only acquired assets without touching DKN, and gives a clean boundary to retire later | When Peachtree is fully absorbed into DKN OUs |
| 2 | DKNMIG01 placed in OU=Servers,OU=Peachtree,OU=Acquired | Leave in CN=Computers, DKN servers OU, Peachtree Servers OU | It hosts migrated Peachtree workloads, so it should get the merger baseline and the Peachtree admin deny | After Peachtree workloads are rebuilt on DKN servers |
| 2 | Password rules for Peachtree users via a PSO, not the OU GPO | Password policy in GPO_Merger_Security_Baseline, Fine Grained Password Policy (PSO) | A password policy in a GPO linked to an OU only changes local accounts on those computers. Domain user password rules come from the domain policy or a PSO | If Peachtree users move to the standard DKN policy |
| 2 | Baseline GPO carries only a legal notice and a 15 minute inactivity lock | Full hardening baseline now, minimal baseline now | Small and provable on day one. More settings get added after the migrated apps are tested | After Day 6 service account work |
| 2 | Deny local and RDP logon for PEACHTREE\Domain Admins on OU=Acquired | Trust selective auth, deny logon GPO, remove admins from Peachtree groups | The forest trust lets old Peachtree admins authenticate here. A deny right blocks them even if a group membership slips through | When the Peachtree forest is decommissioned |
| 2 | PSO_Peachtree_Migrated_Users (14 chars, 24 history, lockout 5 per 15 min) applied to GG_Peachtree_Migrated_Users | PSO on users, PSO on a group, change Default Domain Policy | PSOs can't target OUs, and changing the domain policy would hit every DKN user. A group is one place to add and remove migrated users | When migrated users move to standard DKN policy |
| 2 | Stamp DKN on human users only: HR, IT, Sales, Week8_Automation (17), including disabled mbell | Stamp everyone, stamp enabled only, stamp humans only | Source company describes a person. Built-ins, the PEACHTREE$ trust account, and PAM accounts are not people. Leavers keep the stamp because audits still ask where they came from | When new DKN user OUs are created |
| 2 | Note: DKN Week8_Automation users have no employeeID | Fix now, fix on Day 5 | Day 5 correlation needs employeeID on both sides. Logged now so the gap is visible before it causes a bad match | Day 5 |
| 3 | SID history allowed across the forest trust (/enablesidhistory:yes) | Leave blocked, allow temporarily | Migrated users need their old Peachtree SID to reach Peachtree shares during cutover | After shares are re-permissioned, then turn it back off |
| 3 | IAMLAB\Administrator added to PEACHTREE builtin Administrators for the migration | Dedicated migration account, reuse domain admin | Lab shortcut. A real migration uses a named, time boxed migration account with just enough rights in both domains | Closed on Day 3, see the removal row below |
| 3 | Do not migrate Peachtree admin and itadmin (Domain Admins) | Migrate everyone, migrate people and service accounts only | Migrating a foreign forest's Domain Admins with SID history would carry privileged SIDs into iamlab. Admins get new tiered DKN admin accounts instead. Script 06 shows Missing 2 on purpose | Never |
| 3 | Generated complex passwords for migrated users, not password migration | Migrate passwords with Password Export Server, generate new ones | PES is a separate legacy install on the source DC. Users get a reset at cutover instead. The generated password file stays on DKNMIG01 and is blocked by .gitignore | Before a real cutover |
| 3 | Name collision rule: Peachtree jsmith becomes jsmith_pt through an ADMT include file | Rename with a suffix, merge into the existing account, skip | Merging would hand Jamie Smith (DKN) Jordan Smith's (Peachtree) identity and access. Skipping leaves Jordan with nothing. A suffix keeps both people separate, and the include file makes the rename repeatable instead of a manual fix | When a company wide naming standard replaces the _pt suffix |
| 3 | Seeded a DKN jsmith (Jamie Smith, Sales) to force the collision, stamped DKN at creation. DKN count went from 17 to 18 | Simulate the collision, skip the test | A merger always has duplicate usernames. Testing it on purpose is how ADMT's group membership bug (troubleshooting row 11) got caught. Verified by whenCreated, and all 9 blank stamps are non human by design | Never, it's a real DKN user now |
| 3 | Migrated sqlsvc, backup, reportsvc into OU=ServiceAccounts with SID history, but the PEACHTREE accounts still run the services | Cut services over now, migrate accounts now and cut over later | ADMT generates new passwords, so cutting over now would break SQL and the backup jobs. Service cutover is its own change window | Day 6 |
| 3 | ADMT left the SPN MSSQLSvc/ptsql01 on PEACHTREE\sqlsvc (IAMLAB\sqlsvc verified empty) | Copy the SPN now, move it at cutover | SPNs must be unique in the forest. A duplicate breaks Kerberos for SQL. Move it with setspn in one step at SQL cutover | Day 6, SQL cutover |
| 3 | Accepted ADMT disabling "password never expires" on all 3 service accounts (WRN1:7874) | Turn never expires back on, accept it, move to managed credentials | Never expires is the risk we're trying to get rid of. Each account moves to a credential that rotates itself: a gMSA for reportsvc, CyberArk managed rotation for sqlsvc and backup | Day 6 |
| 3 | Logged RC4-HMAC on the inter forest referral ticket (krbtgt/PEACHTREE.LOCAL). Everything else uses AES-256 | Fix now, fix later | Changing trust settings in the middle of the access test would muddy the results. Fix: enable "The other domain supports Kerberos AES Encryption" on both sides and recheck klist | Day 4, before Entra Connect |
| 3 | Proved SID history access with a Peachtree only share (Dispatch, PT_Ops_Dispatch only) plus a control user (Jamie) | Positive test only, positive test plus a denied control | A positive test alone could mean the share is wide open. The denied control proves access came from SID history and nothing else | When SID history is turned off, rerun the test to confirm the share is re-permissioned |
| 3 | Removed IAMLAB\Administrator from PEACHTREE\Administrators after migration and testing | Leave it until the project ends, remove it right away | Temporary cross forest admin access that never gets removed is a classic audit finding. Removed same day with before and after evidence (20, 20a) | If ADMT is needed against Peachtree again, re-add it as a new, time boxed, logged change |
