## Lessons

1. **Check DNS before blaming the trust.** The wizard's "Kerberos V5 realm" question was really a DNS failure in disguise.
2. **After a fix, test the exact thing the failing tool needs** (the SRV record, not just the domain name), and clear caches before deciding the fix didn't work.
3. **A failing verification tool is not a failing system.** Read what the tool was actually doing when it failed, then confirm with a second independent tool.
4. **Windows error text describes the symptom, not always the cause.** Check the literal claim (memory), then check what you actually care about (routing rules).
5. **A negative test has to try the thing you're protecting.** "Can she connect?" and "can she read the data?" are two different questions.
6. **Verify the network before touching the domain.** Static IP, DNS pointing at a DC, then `nltest /dsgetdc`. A member server with DNS set to 127.0.0.1 is asking itself for directions.
7. **Paste one command at a time.** Pasting a block is how I ran a domain join before I checked DNS.
8. **New computers land in CN=Computers unless told otherwise.** Containers can't hold GPO links. Join with -OUPath, pre-stage the object, or use `redircmp` to send new computers to a staging OU that has a baseline.
9. **`CN=` means container, `OU=` means organizational unit.** Only OUs, sites, and the domain take GPO links.
10. **Prove the setting landed, not just the GPO.** gpresult shows the GPO applied, the registry shows the values, and the logon banner shows the user experience.
11. **A GUI crash doesn't tell you what was saved.** Check the directory itself before redoing anything, especially for permanent changes like the schema. Redoing a schema step that already worked could create a duplicate or conflicting object.
12. **Know which copy of a script you're running.** The host and the VM each had a copy, and only one was updated. A quick Select-String for the changed line proves the version before you trust the output.
13. **A failed create can still create something.** New-ADUser makes the account before it sets the password, so a password error can leave a disabled half account behind. Check what exists before retrying.
14. **"0 errors" is not "0 problems."** ADMT reported a clean run while it was granting a DKN employee another person's Peachtree access. Read migration logs line by line, and check group membership on any account involved in a name conflict.
15. **Two stale script runs in two days is a process gap, not bad luck.** Rows 9 and 12 had the same root cause. Now a `Select-String` version check runs before any updated script, every time.
16. **In a two forest lab, read the tab name and the domain in the error.** The same cmdlet means a different directory depending on which DC you're on. "Cannot find an object" can mean "you're looking in the wrong forest."
17. **When PowerShell says a share "does not exist," ask `net use` for the real error number, then check `klist`.** No tickets means authentication failed before permissions were ever checked. The lockout also proved the PSO enforces in real life, not just on paper.
18. **Authentication is not authorization.** Jamie got a valid Kerberos ticket for PTDC01 and still couldn't even list the folder. I learned this on Day 1 (lesson 5) and still expected net use to fail on Day 3. The habit to build: always test the data, never the connection.
19. **Echo what you typed before you use it.** A Read-Host prompt took only ".onmicrosoft.com", and the scan still "worked" because both accounts were wrong the same way. One `$domain` check would have caught it.
20. **Keep extra tooling off Tier 0 servers.** The sync server holds DCSync rights. Admin tools like Graph PowerShell run from an admin workstation, not from the box an attacker most wants.
21. **Check which PowerShell you're in before troubleshooting a module.** Windows PowerShell 5.1 and PowerShell 7 have different module paths and runtimes. `$PSVersionTable` takes one second.
22. **Tell the sign in which tenant, and read the consent screen.** `-TenantId` stopped the broker treating a work account as a personal one. Consent stayed user only, because admin consent is a tenant wide decision.
23. **A green dashboard means "no errors reported," not "no problems."** Sync, Connect Health, and Graph all said fine while an alias was missing. Check the source against the target.
24. **Fix the file, not the policy.** Unblock one reviewed script instead of setting Bypass for the whole machine.
25. **Scrub for every form an identifier can take, not just the obvious one.** Guest UPNs embed the person's real email, and the scrub command itself can leak what it's scrubbing into a screenshot.
26. **A tool's label isn't proof of the permission.** dsacls showed the member grant as "Add/Remove self as member" because both rights share the same GUID. Get-Acl showed the real right, WriteProperty on member. When a label looks wrong, check the raw ACL before changing anything.
27. **Read the logs and the source before guessing.** "Details for at least one Domain/Forest is required" made it look like the settings were lost. The Debug page proved the app had never saved, the Tomcat log pointed to saveDomains, and discoverDomains.xhtml showed the cause. The grid rows had been typed but never added with the Add button. Three guesses failed, and the evidence found it on the first try.
28. **Correlation can be set up perfectly and still lose.** When the real match finds nothing, a display name can quietly do the matching. Every identity needs a unique, permanent key on every path, not just the configured one.
29. **Listening locally doesn't mean reachable.** IQService answered on port 5050 inside DKNMIG01 but timed out from the host. Proving the service worked locally narrowed it to the firewall, and the fix was a rule scoped to one host IP, not an open port.
30. **The screen shows what you picked. The stored object shows what was saved.** Both owners displayed as "Marcus Reed", so the catalog couldn't prove which one owned the helpdesk groups. The Debug XML showed name="PT1003". When two people share a name, check the stored key before calling it done.
31. **Impact analysis measures change, not current state.** I expected the new IT role to report the 12 people who already held PT_All_Staff. It reported 0 gains, 0 losses, 0 conflicts, which was correct, because a role nobody is assigned to changes nothing. Know what a report measures before deciding whether its number is good.
32. **A severe error is just a log entry you haven't read yet.** Incident 57 looked scary, but the SyslogEvent named the exact failure: a workflow evaluating an empty changes list. A second identical failure proved it wasn't transient. Confirm nothing is lost before cleaning up, and don't patch vendor workflows to clear one stuck item.
33. **A summary counter is not the identity.** The rerun showed no "Role changes" line, so it looked like the rule fix failed. Jordan's Entitlements tab showed All Employees was gone. Check the object, not the tally.
34. **After a merger, every "everyone" rule is a question.** Two pre-merger rules said "every active employee." One quietly gave a Peachtree user a DKN birthright role, the other provisioned a DKN account. Scope matters most where nobody thought to write it down.
35. **Contain first, then fix it properly.** Disabling the account cut the access in minutes. The real fix, adding Delete to the rule, went through the system of record with a before and after, instead of a hand edit in the target database.
36. **A joiner with no leaver is half a lifecycle.** The DKN_Portal rule could create accounts but never remove them, and nobody noticed until one had to be removed. Test the exit path when you build the entry path.
37. **Scope joiners by who should get access. Scope leavers by who has it.** The DKN Joiner needed company = DKN because it grants access. The DKN Leaver stays open to everyone because it only removes DKN_Portal accounts from whoever holds one, which would also clean up a stray account like PT1003's.
38. **An SoD violation needs an owner who isn't the violator and isn't missing.** The only person breaking the rule was the Finance Manager, and she had no manager on record. Default routing would have sent the violation to her, or to nobody. Pick the reviewer before the policy goes live.
39. **Read the rule the approval shows you, not the one you meant to build.** All four role changes said OR instead of AND. One word would have given every DKN employee ERP admin rights. Approval steps feel slow until they're the only thing between a typo and production.
40. **Aggregation updates accounts, refresh updates conclusions.** After removing Maria from a group, her entitlements showed the change right away but her detected role still showed the old access. Roles are recalculated only on an identity refresh. Read the entitlements for facts, and refresh before trusting the role view.
41. **A role that only labels access is a report. A role that provisions is a control.** Removing Maria from her group by hand and watching IIQ add her back proved the roles enforce access, not just describe it.
42. **A change needs a before.** Lifecycle events compare against a snapshot that only exists after an identity's first event-processing run. Migrated identities need that baseline pass before any leaver can fire. I had two wrong theories first; watching the snapshot across four runs is what proved how it works.
43. **Proofread a review before the reviewer sees it.** Staging showed Dana's review held only her 4 Peachtree reports and only Peachtree AD access. Roles also shrink a review: groups a role already explains fold into the role line, so only unexplained access shows up on its own. GG_Peachtree_Migrated_Users landed on every person as a technical group a manager can't judge, and noise like that is what trains reviewers to click Approve without reading.
44. **Know when a click becomes final.** Decisions sit as a draft until saved, and Prompt for Sign Off fires the moment the last open item is decided. Dana's review was signed before the planned comment got added, and a signed review is read only. Anything that needs to be on the record gets added before the last decision, not after.
45. **Rebuilding a config by hand means rechecking every setting.** IIQ doesn't clone a certification schedule, so Kiran's was rebuilt from scratch. Three settings came back as defaults (Included Applications empty, Show Elevated Access off, subordinate managers on) and were caught tab by tab before scheduling. An empty application list means every application, not none.
46. **A signature is recorded right away, but the phase change runs in the background.** Right after Kiran signed, the admin view still showed 0/1 reviews complete and Phase Active, even with 9/9 items and a sign date. A minute later a background job moved it to Revocation. A screen taken right after an action can show the before state, so refresh before deciding something failed.
47. **Manager reviews only cover people whose manager has a review.** Dana, Kiran, and PT1003 reviewed 9 people between them, and none of the 3 managers were reviewed themselves, even though they hold the most access in Peachtree. Staging showed the gap before anyone signed. A targeted review by an independent team closes it.
48. **Folding access into a role can hide what makes it risky.** Show Elevated Access marks elevated entitlements, but PT_IT_Helpdesk_Admin was inside the PT Systems Administrator role, so Nia's line had no marker. The role description has to say what it grants, or the reviewer can't see the risk.
49. **A different screen means different defaults.** The targeted certification used a one page layout with looser defaults than the manager wizard: bulk approve on, no comments on revoke, self certification open to certification admins, and partitioning on with an empty partition count. Every setting was rechecked against the manager reviews before scheduling, instead of assuming the same choices carried over.
50. **A revoke isn't done until the target system says so.** The certification showed two revokes, but proof came from AD: PT_Ops_Warehouse gone from Dana and PT_IT_Helpdesk gone from PT1003, with nothing else touched. Before and after membership queries on both sides of the review turn "the report says fixed" into "the directory shows fixed."
51. **Prove a revoke sticks, not just that it happened.** After the targeted review removed two groups, an aggregation (12 optimized, nothing to catch up on) and a provisioning refresh on just those two people (2 examined, nothing re-added) showed the role design agrees with the review. A revoke that a later refresh quietly puts back is worse than none, because the report says it's fixed.
52. **Check what an export leaves out before calling it the audit record.** The certification CSV kept every decision and comment but had no reviewer or sign date columns. The attestation (who signed, when) lives in the certification itself, so the evidence pack pairs the CSV with the signed review screenshots instead of relying on either one alone.
53. **Read the source before writing the conclusion.** The retire row first called crm_poweruser an account with no AD object. The spreadsheet showed it was an access line held by nfoster in Old CRM, which IIQ can't see, so the planned "revoke in certification" could never have happened. Checking the original file turned a wrong claim into an honest open item.
54. **An inventory only covers the directory it scans.** Script 09 found 6 accounts in iamlab.local and none of Peachtree's shared Domain Admins, because admin and itadmin still live in peachtree.local. The riskiest accounts in a merger are often the ones in the forest you haven't looked at yet.
55. **A flag can be right for the wrong reason.** The built-in Administrator showed up in a service account scan because its password never expires. It isn't a robot account, but it has the same risk, so it goes to CyberArk instead of being dismissed as noise.
56. **An owner has to be someone who can sign in and answer.** The planned owner for the DKN accounts was E1002 from SailPoint's HR feed, but E1002 has no AD account. HR and the directory are two different populations until someone reconciles them, so owners were picked from enabled AD accounts.
57. **Some names belong to the vendor.** The MSOL account fails the naming standard, but renaming it would break Entra Connect, and its Description holds the tenant name. The control that mattered was a named owner, set through the manager attribute without touching anything Entra Connect relies on.
58. **An empty result needs proof the scan could see.** Script 11 found no usages, which could mean none exist or the scan never reached the server. A known service queried from the same machine over the same path proved it was a real zero. The first check ran on DKNMIG01 itself, which proved SQL's account but not the path, so the proof has to come from where the scan ran.
59. **Evidence should say exactly what happened.** The dry run claimed it saved a file it had skipped, and the empty scan wrote a 0 byte CSV that looked like a crash. Both scripts now say "dry run, nothing written" or write a header with a note naming the servers checked.
60. **A service saying its door is open doesn't mean Windows is using the door.** The Vault logged "Firewall is open for client communication" while every client timed out. Its rule existed but sat in the local store, and the enforced policy ignores local rules on a Public network. Check the ActiveStore, the rulebook Windows actually enforces, not just the rules you can see.
61. **A change outside the lab can break the lab.** A new home router gave Windows a new gateway, so every workgroup server decided it was on a new, Public network. Nothing in CyberArk changed. When something that worked last week stops working, ask what changed around it, then prove each theory with evidence. Two good theories (an IP conflict, a profile scoped rule) were ruled out before the facts found the real one.
62. **A running service never rechecks its password.** After CyberArk changed svc_sql_pt, SQL kept running and every check looked green. The outage waited for the next restart. Test the restart, not just the change.
63. **A password rule written for people can break a vault.** The one-day minimum age stops a person from cycling back to an old password. It also blocked the CPM from changing a password 30 minutes after setting it. Vault-managed accounts need their own policy.
64. **A policy and its generator have to agree.** The PSO's minimum length is 12 because the CPM generates 12 characters. A stricter policy would have failed every rotation with the same 2245 error.
65. **When every fix reveals a new error, look at where the error happens.** The usage failed three times: unreachable, then denied, then unreachable at a different step. Each message named a later stage than the last, which proved each fix worked.
66. **The account that updates a server should not be able to own the domain.** pam_reconcile would have worked in seconds, but a Domain Admin logging in to DKNMIG01 is the kind of exposure tiering exists to prevent. pam_logon_t1 can only touch one server.
67. **Read the prompt before pressing Enter, again.** The WMI change ran on the CPM instead of DKNMIG01. Lesson 16 already said this. The habit to build is checking for Administrator.IAMLAB before any change command, not just reading the tab name.
68. **A name that resolves isn't always resolving the right way.** The CPM found DKNMIG01 as DKNMIG01.local through multicast, not through DNS. It worked on one flat network and would fail across subnets. Use the full name in anything a system depends on.
69. **A failed usage does not stop the password change.** CyberArk changed svc_sql_pt three times (1:15, 1:30, 1:45) while the SQL usage kept failing. Each change left the service one password further behind. A usage error is an outage on a timer, so it gets fixed before the next restart, not after.
70. **A copied platform brings its rules with it.** PT Tier0 Domain Admin was duplicated from Windows Domain Account and inherited its PSM exception without anyone adding it. Here that helped, but a copy is not a clean slate. Check the Master Policy exceptions on every new platform before trusting it.
71. **Read the permission grid, not the plan.** I designed pt_itops as connect only, and the safe gave it Retrieve anyway. The grid is the truth. Review every member's checkboxes after a safe is created, before any account goes in.
72. **Policy and permissions are two separate locks.** The PSM rule blocks Show and Copy today, but a Master Policy exception can be turned off with one click. Removing Retrieve at the safe level means the password stays hidden even if the policy changes.
73. **In the classic safe page, permission headings are collapsed links.** Authorize account requests sits under Workflow and only shows up after you click the word. A dual control setup can look complete while nobody actually has the right to approve.
74. **Verify before you trust a vaulted password.** I typed the wrong password during onboarding, and Verify caught it with a clear 1326 before the CPM changed anything in AD. Fixing the vault's copy is a one minute job. Fixing a rotated Domain Admin password nobody knows is not.
75. **A failed login is also a free audit.** The bad password test showed BadLogonCount 1 and LockedOut False on two Domain Admins, which led straight to LockoutThreshold 0 in peachtree.local. Inherited domains hide weak defaults. Check the policy before you trust it.
76. **Platform password rules apply to people too.** PVWA would not accept the old seeded Domain Admin password because it had one uppercase letter and the platform requires two. The vault refused to store a password weaker than the ones it makes itself, which is the right call. The fix was a compliant reset in AD, not a weaker platform.
77. **Fix the policy before the rotation, not after the error.** In Part A the CPM hit 2245 on svc_sql_pt and the PSO came after. In Part B the PSO went in first, and PEACHTREE\admin rotated 16 seconds after the change was queued, with no failure. Same lesson, applied before it could cost anything.
78. **A password reset does not unlock a suspended vault user.** pt_itops kept failing after the reset because the vault had already suspended it, and PVWA shows the same "Authentication failure" for a wrong password and a suspended user. When a reset does not fix a login, check Disable User in PrivateArk before resetting again.
79. **italog is not a full login audit.** It recorded the earlier Administrator failures but nothing for pt_itops, and I wrongly read the gap as "the request never reached the vault." The user's own properties gave the answer. Do not treat a missing log line as proof of anything.
80. **A dual control test needs a no, not only a yes.** Request 1 accidentally asked for 49 hours of Domain Admin access. Rejecting it with a reason proves the approver is a real check. An approval alone only proves the button works.
81. **Dual control is only as strong as what the approver reads.** Request 1 was rejected because the wrong date showed in the list. Request 2 was approved with a 13 hour window because the end time was cut off, and the approver clicked Confirm without opening it. The control worked as designed. The review did not. Open every Tier 0 request before you approve it.
82. **Defaults are decisions someone else made for you.** The PVWA request form opens with a two day window every time. Request 1 was not just a typo. The requester accepted a default that gives Domain Admin access for 49 hours. Check every default on a Tier 0 form before you trust it.
83. **Preflight saves the approval window.** The request had 35 minutes left, and a 3389 test from PSM showed RDP was closed on PTDC01 before anyone clicked Connect. Five minutes of checks beat a failed session and a confusing PSM error inside a short approval window.
84. **Run hostname before any change.** Rows 37 and 43 are the same mistake: a correct command in the wrong VM tab. Both times, the PowerShell prompt showed which machine I was on, and I did not read it. Making hostname the first command of every change turns a habit I keep forgetting into a check I can see in the screenshot.
85. **The first privileged session is also an audit.** I connected to check Domain Admins membership because it was the reason on the request, and the output showed a third Domain Admin the vault does not hold. Vaulting the accounts you know about is not the same as vaulting all of them. Check the group from inside the session.
86. **The recording is the proof, not the approval.** An approval only says someone was allowed in. The PSM recording shows what they actually did, with a process timeline an auditor can search. Request 3 was approved for one hour, and the recording shows 1 minute 55 seconds of real work inside that window.
87. **Check the evidence file, not just the screen.** The gMSA was created correctly, but the script's evidence said the DNS name was blank and wrote a type name where 30 should be. On screen {30} looked fine. In the CSV it was useless. Read what was exported before you call it proof.
88. **Every gMSA name ends in $, so quote it with single quotes.** Double quotes in PowerShell expand variables, and gmsa_reports_pt$ followed by a colon broke the parser before icacls ran. The error came from PowerShell, not from Windows permissions, which is why reading which tool threw the error matters.
89. **An inventory that cannot see the new account is not evidence.** Script 09 used Get-ADUser, which never returns gMSAs, so the after report would have shown the old account gone and nothing in its place. The cleanup would have looked like a loss of coverage instead of an upgrade. Check that your tooling can see the thing you just built.
90. **Pick the tool that fits the workload.** The reports job became a gMSA because Windows can rotate it with nobody involved. SQL and backup went to CyberArk because their passwords need a usage update and a human recovery path. Vaulting everything is not a strategy. Matching each account to what it needs is.
91. **The after inventory should find what you missed.** It came back with IAMLAB\Administrator flagged on four issues, the same gap the PSM session showed for Peachtree. A cleanup report with zero findings would have meant the tool was blind, not that the work was perfect.
91. **A scheduled workflow starts running the day it is committed.** The agent's workflow failed twice on its Monday schedule before it had an identity. It failed closed, which is the right way to fail, but the schedule doesn't wait for you to be ready.
92. **Read the form before following the notes.** Entra's GitHub form asked for IDs my own workflow comments didn't mention. Ten minutes of reading explained the change and saved an afternoon of debugging a subject mismatch.
93. **Names can be reused. IDs can't.** A trust built on a repo name passes to whoever creates a repo with that name next. Owner and repo IDs are assigned once, so the immutable subject keeps the trust tied to this repo.
94. **Existing is not the same as configured.** GitHub had already created access-agent, empty and open to every branch. Anything a system creates for you on the side starts with nobody's rules on it.
95. **A negative test has to fail at the control you are testing.** Without repository secrets, the wrong subject test would have failed on a missing client ID and never reached Entra. A failure for the wrong reason looks exactly like a pass. Lesson 5 again, in a new tool.
96. **Treat CI logs as public.** I blurred the extension app ID in every screenshot, and the agent printed it in plain text in a run log. Fix it where it is written, in the code, then delete the run that holds the old copy.
97. **Prove least privilege in both directions.** The green run proved the agent could read. A 403 proved it couldn't write, and AADSTS700213 proved the trust only opens for the approved job. All three belong in the evidence.
98. **Write the guess down so you can prove it wrong.** Row 21 said "likely the tenant domain." The retest said no. Updating the row is worth more than leaving a confident guess in the record.
99. **Fail at the real cause.** Script 08 kept going after a canceled sign in, and its last error told me to check Entra Connect. -ErrorAction Stop makes the script stop at the first real problem instead of three steps later.
100. **Delete the old key once the new one is proven, then prove the old one is gone.** The secret came off the app only after a federated run passed, and a local run without it failed with CredentialUnavailableError. Removing a secret and proving it's gone are two separate steps.
101. **Read git status before every commit, and prove a duplicate before you delete it.** 22 files looked like new Day 6 work and were really old names that came back. Committing them would have broken the index, and deleting them on a guess could have lost a real screenshot. A hash match against the committed twin made the delete safe.
102. **Suppress a false positive by its fingerprint, never by turning off the rule.** gitleaks flagged a screenshot filename as an API key. Ignoring that one finding keeps the scanner watching the same file and every other file for real secrets. Disabling generic-api-key would have hidden the next real one too.
